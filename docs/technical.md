# Техническая документация

[← Вернуться к README](../README.md)

Подробности реализации методов загрузки и ограничения поддерживаемого набора PE.

## Реализация и ограничения

- OpenProcess с необходимыми правами, VirtualAllocEx только PAGE_READWRITE, запись Unicode-пути, CreateRemoteThread с LoadLibraryW.
- Адрес загрузчика вычисляется по смещению в фактическом системном модуле (учитываются forwarded exports), а не слепым копированием локального адреса. Предполагается одинаковая версия системного модуля в обоих процессах на одной Windows.
- Проверяются PE, DLL-флаг, отсутствие CLR-заголовка, архитектура процесса и время запуска из списка.
- Успех подтверждается наличием DLL в модулях процесса, а не усечённым до DWORD указателем HMODULE.
- Ожидание 15 секунд. При таймауте поток не прерывается и буфер пути не освобождается: он может ещё использоваться. Несколько килобайт остаются до завершения процесса. Результат неизвестен; не повторяй операцию вслепую.
- Ошибка зависимостей и отказ DllMain не дают точного удалённого GetLastError. Нужна отладка DLL.
- DLL должна выполнять минимум работы в DllMain: загрузчик удерживает loader lock.
- Выгрузка, скрытие, обходы защиты и автоматический повтор не реализованы.
- Проверка пути модулей не нормализует симлинки/alternate file names.

## LdrLoadDll Stub

Метод выбирается в поле Method. Используется экспорт ntdll!LdrLoadDll и небольшой stub соответствующей архитектуры (x64 или x86). Код выделяется как RW, затем переводится в RX; данные остаются RW. Перед запуском сбрасывается instruction cache. NTSTATUS и полный указатель модуля читаются из отдельного блока данных. Успех дополнительно проверяется по списку модулей процесса.

При таймауте код и данные остаются в процессе: поток может продолжать их использовать. Автоматического повтора нет. Совпадение архитектур обязательно. Системные ограничения на динамический код могут запрещать запуск stub; обходы этих ограничений не реализованы.

## Thread Hijacking

Перенаправляет существующий доступный поток; новый поток для загрузки не создаётся. Предварительно приостановленные потоки пропускаются. Контекст, включая включённые XState/AVX-регистры, сохраняется через InitializeContext/GetThreadContext и восстанавливается через NtContinue. Используется существующий стек потока, исходный LastErrorValue сохраняется. Загрузка выполняется через LoadLibraryW.

Момент прерывания произвольного потока может оказаться неподходящим для вызова загрузчика: возможны зависания или ошибки целевого приложения. Ожидание ограничено 15 секундами. При таймауте поток принудительно не прерывается; результат неизвестен. Код, путь и сохранённый контекст остаются в процессе до его завершения и при успешной операции: NtContinue может ещё читать их после сигнала о завершении вызова. Успех загрузки проверяется по полному HMODULE и списку модулей, но это не доказывает корректность приложения после перенаправления.

## Manual Map

Поддерживается ограниченный набор нативных PE DLL: размещение заголовков и секций, релокации HIGHLOW/DIR64, импорты по имени и ordinal, forwarded exports/API-set imports через GetProcAddress в целевом процессе, права памяти секций, регистрация x64 runtime function table и вызов точки входа с DLL_PROCESS_ATTACH. Память кода временных вызовов переводится из RW в RX.

До выделения удалённой памяти проверяются границы таблиц импортов, терминатор дескрипторов, имена, таблицы lookup/IAT и зарезервированные биты ordinal. Отсутствие OriginalFirstThunk допускается: используется IAT. Структура блоков релокаций, типы и границы исправляемых указателей проверяются независимо от будущего адреса размещения. Эти проверки не доказывают корректность произвольного кода DLL.

Не поддерживаются статический TLS и TLS callbacks, delay-load imports, x86 SafeSEH и Guard CF/XFG load configuration. Такие образы отклоняются с явной ошибкой; DLL с другим неподдерживаемым поведением может потребовать системный загрузчик. Не выполняется регистрация образа в системных списках загрузчика, поэтому GetModuleHandle, thread notifications и механизмы, рассчитывающие на такую регистрацию, для образа не работают как при обычной загрузке.

Повторная ручная загрузка отслеживается только в текущем сеансе приложения. После перезапуска приложения ранее размещённые образы автоматически не обнаруживаются. Выгрузки нет. Загруженные зависимости остаются с удержанными ссылками, в том числе при последующей ошибке. Если DllMain уже вызван или удалённый вызов имеет неизвестное состояние, память образа сохраняется: код DLL мог опубликовать указатели или создать потоки. Перед повтором после такой ошибки требуется перезапустить целевой процесс.

## LdrpLoader: закреплённый приватный ABI

Отдельный метод x64 для сборки ОС 26300. Проверенный файл ntdll.dll: 10.0.26100.9549, SHA-256 `651AC9041AF8E6B5EBD331D53163244C0A27D36D1433F0F15CAC1F28C5F2E82C`. Символы Microsoft: `ntdll.pdb`, GUID `C031D45B-0DA1-8A6E-74D0-6ED6AB2DD9E1`, age 1. RVA: LdrpInitializeDllPath `0x91C80`, LdrpLoadDll `0x2A630`, LdrpDereferenceModule `0x225F0`. Эти значения подтверждены символами и сравнением последовательности вызовов в LdrLoadDll установленного бинарника; перенос на другую версию требует нового анализа и тестов.

Один удалённый поток выполняет подготовку 128-байтового контекста пути, LdrpLoadDll, условный RtlReleasePath и LdrpDereferenceModule. Сохраняются NTSTATUS и полный DllBase из LDR_DATA_TABLE_ENTRY. Успех дополнительно подтверждается совпадением HMODULE со списком модулей. Перед выделением удалённой памяти проверяются архитектура, сборка ОС, хеши локального и целевого файлов ntdll, PE/COFF-заголовок, размер образа и первые 32 байта трёх приватных функций в целевом процессе. Это ограниченная проверка идентичности, а не полная проверка целостности памяти ntdll.

Код выделяется RW, переводится RX, затем сбрасывается instruction cache; данные остаются RW. При таймауте или неподтверждённом возврате временные блоки сохраняются до завершения процесса; повтор автоматически не выполняется. Никаких запасных вызовов другого метода при несовпадении бинарника нет. x86 явно отклоняется. Проверки на неподдерживаемых системах подтверждают отказ, а сценарий выполнения LdrpLoader пропускают.

## Компоненты

Views обращается к Services; методы Loading используют общий Interop. PortableImage отвечает за чтение PE, проверки и релокации; RemoteExecution — за удалённые вызовы и временные буферы. ThreadContext сохраняет расширенный контекст потока. Пространство имён проекта — CompactLoader.

Векторный исходник — Assets/AppIcon.xaml. ICO содержит девять размеров 16–256 px; PNG используется как крупный предпросмотр.
